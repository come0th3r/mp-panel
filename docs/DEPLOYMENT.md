# Развёртывание MP

Панель, PostgreSQL и worker работают на одной Linux-машине в Docker Compose. Minecraft размещается на хостах с отдельным агентом. Подключение нового игрового хоста производится из панели по SSH; переносить веб-приложение на каждый игровой хост не требуется.

## Требования

- Хост панели: Debian или Ubuntu x86_64, root или sudo. Нужны Docker Engine и плагин Docker Compose. При отсутствии Docker установщик предлагает официальный [convenience installer](https://docs.docker.com/engine/install/ubuntu/#install-using-the-convenience-script). Docker предназначает этот способ для разработки и тестовых машин. Для постоянной установки подготовьте Docker через официальный пакетный репозиторий.
- Для скачивания релиза и сборки контейнера нужен доступ к GitHub, npm registry, Go modules, Docker Hub и официальным каталогам Minecraft. При включённом шлюзе нужен также доступ к GitHub Container Registry.
- Игровой хост: Debian / Ubuntu x86_64 с systemd, SSH/SFTP и root или sudo. Агент устанавливает Docker при его отсутствии.
- Хост панели должен иметь достаточно ресурсов для frontend/Go сборки. Сервисы используют PostgreSQL и постоянные Docker volumes.
- Домен панели указывает на HTTP reverse proxy с HTTPS. Отдельное имя агента или тот же домен с портом 8443 должно вести до mTLS listener панели без завершения TLS на HTTP-прокси.

## Установка из релиза

Скачайте файл `setup.sh` из нужного релиза на машину панели и запустите его:

```sh
sudo bash setup.sh
```

Установщик запросит адрес панели, HTTPS-адрес агентского канала и контактный email администратора для каталога Paper. Затем можно выбрать игровой шлюз (`none`, `mc-router` или `gate`) и существующую Docker-сеть Nginx Proxy Manager. При установке шлюза понадобится игровой домен и локальный TCP-порт.

Без параметра `--source` отдельный установщик скачивает архив `mp-panel-v0.4.1.tar.gz` из релиза и проверяет его по `SHA256SUMS`. Он создаёт каталог `/opt/mp-panel`, генерирует пароль PostgreSQL, сохраняет `.env` с правами 0600, собирает контейнеры и ждёт готовности API. После первой установки выводится токен создания владельца. Minecraft-серверы создаются отдельно в панели.

Если исходники уже скачаны, можно установить панель из каталога или архива:

```sh
sudo bash deploy/setup.sh --source /path/to/mp-panel
sudo bash setup.sh --source /path/to/mp-panel-v0.4.1.tar.gz
```

Справка доступна без установки:

```sh
bash setup.sh --help
```

Параметр `--directory` задаёт другой каталог установки. `--version` выбирает версию релиза, а `--repository` задаёт репозиторий в формате `owner/name`. Для запуска без вопросов используйте `--yes` и явно укажите контакт, адреса и нужные настройки; этот режим также разрешает установку Docker.

В новой установке веб-порт по умолчанию публикуется на `0.0.0.0:8080`. Адрес можно ограничить параметром `--web-bind 127.0.0.1`, если доступ идёт через локальный reverse proxy или SSH-туннель. Установщик не получает HTTPS-сертификат панели, не создаёт DNS-записи и не настраивает NAT. Для адреса панели с HTTPS значение `MP_COOKIE_SECURE` будет `true`; для HTTP оно будет `false`.

## Обновление и откат

Для обновления скачайте новый `setup.sh` из релиза и запустите его с прежним каталогом. Существующий `.env` сохраняется целиком. Установщик использует действующие Compose-файлы из регистрации контейнера, включая NPM и игровой шлюз. Он сохраняет их без изменений, поэтому новые параметры или изменения схемы Compose из релиза не включаются автоматически. Персональные файлы вне каталогов исходников также сохраняются.

Обновление выполняется под блокировкой `flock`. Пока новая версия собирается в отдельном каталоге, прежняя панель продолжает работать. API и worker используют отдельные теги новой сборки, прежние Docker image IDs сохраняются вместе с архивом образов. При незавершённых управляющих заданиях обновление прекращается: сначала дождитесь установки серверов, файловых операций и подключения хостов.

Перед переключением останавливаются только API и worker. PostgreSQL и игровой шлюз продолжают работать. Установщик создаёт согласованную копию PostgreSQL, копию `panel-data` с ключами и полный снимок каталога установки. Затем обновляет исходники, запускает ранее работавшие сервисы и ждёт готовности API. Если сборка или копирование не удалось, прежние сервисы возвращаются без восстановления базы. Если новая версия успела запуститься и не прошла проверку, восстанавливаются база, ключи, прежние исходники и образы. Намеренно остановленные ранее API/worker остаются остановленными.

Копии сохраняются с доступом только root в `/var/lib/mp-panel-updates/mp-panel/<ID>`. Для операции требуется минимум 4 GiB свободного места плюс размер копий; точный расход Docker-сборки зависит от кеша и зависимостей. Установщик не удаляет игровые миры, пользователей, маршруты, DNS и Docker volumes. Игровые контейнеры на хостах продолжают работать.

В старых установках нет списка файлов исходников. При первом обновлении такими файлами считаются каталоги приложения `cmd`, `internal`, `apps/web/src` и известные файлы сборки. Их локальные изменения сохраняются в снимке, но активный код заменяется релизом. Для последующих обновлений записывается `.mp-source-files.json`, чтобы удалять устаревшие файлы исходников без удаления других пользовательских файлов.

### Восстановление прерванного обновления

При обычной ошибке установщик пытается восстановить прежнюю версию автоматически. При выключении питания, `SIGKILL`, недоступности Docker или неудавшемся откате может потребоваться ручное восстановление. Это не атомарная операция для аварии хоста. Не удаляйте каталог копии и контейнеры до проверки: состояние запуска новой версии используется при решении о восстановлении базы.

В сообщении об ошибке выводится готовая команда для конкретной копии. Общая форма:

```sh
sudo bash /var/lib/mp-panel-updates/mp-panel/<ID>/recover.sh --recover /var/lib/mp-panel-updates/mp-panel/<ID>
```

Замените `<ID>` идентификатором из сообщения. Команда проверяет защищённый каталог и состояние транзакции, получает ту же блокировку и продолжает откат. Если сервисы не удаётся остановить или нельзя определить, запускалась ли новая версия, восстановление данных прекращается до исправления проблемы с Docker. Если новая версия успела принять незавершённые управляющие задания, откат также не заменяет базу: такие операции нужно сначала разобрать, чтобы не потерять их регистрацию. Повторный запуск восстановления завершённой транзакции отклоняется. Данные резервных копий содержат секреты и не предназначены для публикации.

### Обновление агентов

Панель и агент обновляются отдельно. Новый веб-интерфейс может работать со старым агентом, который продолжает применять прежние ограничения загрузки. Обновите панель установщиком, затем каждый игровой хост:

1. Войдите как владелец и откройте «Хосты».
2. Выберите существующий хост, на котором находится нужный Minecraft-сервер.
3. Нажмите «Обновить агент»; для хоста не на связи нажмите «Повторить подключение».
4. Укажите SSH-доступ к этому хосту, проверьте fingerprint и дождитесь успешного задания.
5. Обновите страницу. В карточке хоста версия агента должна соответствовать установленному релизу панели.

Обновление сохраняет регистрацию хоста и игровые данные. Новый хост создавать не требуется. Начиная с v0.3.4 агент сообщает свою версию; более ранние сборки показываются как «Не сообщает версию». Это само по себе не означает ошибку: агент v0.3.3 уже поддерживает загрузку без ограничений количества и размера.

Ошибки `upload needs a verified panel artifact, at most 256 MiB per file` и `select between 1 and 100 paths` при загрузке папки означают, что файлы получил агент с прежними ограничениями. Обновление только панели их не снимает. После обновления агента повторите загрузку.

Размер загрузки и размер распаковки различаются. Актуальный агент принимает обычные файлы больше 2 ГиБ и папки с любым количеством файлов при наличии места на диске. Для распаковки ZIP/RAR отдельно действует предел 2 ГиБ извлечённых данных и 10 000 записей. Большой мир можно предварительно распаковать на компьютере и передать в панели через «Выбрать папку…».

Версию агента v0.3.4 и новее также можно посмотреть на игровом хосте:

```sh
/usr/local/bin/mp-agent --version
```

## Ручная настройка

Если устанавливаете панель вручную или через SSH-инструмент для Windows, скопируйте `.env.example` в `.env` и задайте:

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL. Используйте hex-строку, например вывод `openssl rand -hex 32`: она не требует URL-экранирования в DATABASE_URL. |
| `MP_PUBLIC_URL` | Полный внешний URL панели, например `https://panel.example.com`. |
| `MP_AGENT_PUBLIC_URL` | URL, доступный со всех игровых хостов, например `https://agents.example.com:8443`. Имя попадёт в внутренний серверный сертификат. |
| `MP_DOWNLOAD_USER_AGENT` | Имя приложения с вашей реальной контактной ссылкой или email. Paper требует такой [User-Agent](https://docs.papermc.io/misc/downloads-service/). |
| `MP_COOKIE_SECURE` | `true` для HTTPS. Для доступа через локальный HTTP SSH-туннель в тестовой среде используйте `false`. |
| `MP_WEB_BIND` / `MP_WEB_PORT` | По умолчанию `127.0.0.1:8080`, доступ через proxy или SSH-туннель. |
| `MP_AGENT_BIND` / `MP_AGENT_PORT` | По умолчанию `0.0.0.0:8443`; TLS требует сертификат зарегистрированного агента. |

`.env` не добавляется в исходный архив или Docker build context. SSH-инструмент передаёт его отдельным файлом с правами 0600. Не меняйте пароль существующей базы простой заменой `.env`: для работающего PostgreSQL требуется отдельная смена пароля роли.

## Установка всего веб-приложения по SSH с Windows

Для интерактивной установки скачайте `setup.ps1` из [релиза](https://github.com/come0th3r/mp-panel/releases/tag/v0.4.1) и выполните:

```powershell
.\setup.ps1 -Address 203.0.113.10 -User root
```

Этот сценарий требует только PowerShell и OpenSSH на компьютере администратора. Он скачивает Linux-установщик на удалённой машине и запускает его с вопросами. SSH запрашивает пароль и подтверждение ключа хоста; при работе через обычного пользователя sudo запрашивает пароль отдельно. Параметры `-Port`, `-IdentityFile`, `-InstallDirectory`, `-Version` и `-Repository` позволяют изменить адрес установки и релиз. Пароли в файлы не записываются.

Для отправки локальных исходников используется отдельный сценарий `deploy/deploy.ps1`:

На компьютере администратора нужны PowerShell, OpenSSH (`ssh`, `scp`) и `tar`. Используйте SSH-ключ или ssh-agent. Для сценария без интерактивного ввода нужен root либо пользователь с passwordless sudo.

Сначала проверьте SSH fingerprint через консоль сервера или другой доверенный канал и добавьте подтверждённый ключ в `known_hosts` обычным SSH-подключением. Скрипт использует `StrictHostKeyChecking=yes`, не принимает неизвестные или изменившиеся ключи автоматически.

После заполнения `.env` из корня проекта:

```powershell
.\deploy\deploy.ps1 -Address 203.0.113.10 -User root -IdentityFile C:\Users\you\.ssh\id_ed25519
```

Дополнительные параметры: `-Port 2222`, `-InstallDirectory /opt/mp-panel`, `-EnvironmentFile C:\secure\mp.env`, `-KnownHostsFile C:\secure\known_hosts`.

Инструмент упаковывает локальный проект, загружает архив и настройки через SCP, устанавливает Docker при необходимости и выполняет `docker compose up -d --build --wait`. Если в `.env` задан `MP_NPM_NETWORK`, включается NPM overlay. При `MP_ENABLE_GATEWAY=true` переменная `MP_GATEWAY_PROVIDER=mc-router` выбирает mc-router overlay; без неё используется Gate Lite. Репозиторий по умолчанию размещается в `/opt/mp-panel`. Этот сценарий предназначен для первоначальной установки локальных исходников и не выполняет согласованное резервное копирование или автоматический откат. Для обновления существующей панели используйте новый `setup.sh` с `--source` и прежним каталогом. Docker volumes не удаляются; команда `down -v` не выполняется.

Для заранее скопированного проекта можно установить панель вручную:

```sh
cd /opt/mp-panel
docker compose up -d --build --wait
```

## Первое подключение

На сервере панели получите одноразовый ключ настройки владельца:

```sh
cd /opt/mp-panel
docker compose exec -T api cat /var/lib/mp/keys/setup.token
```

Откройте внешний HTTPS URL, введите ключ, имя и пароль владельца. Затем подключите TOTP-аутентификатор и сохраните резервные коды. API логирует только путь к setup.token, сам токен в логи не записывается.

Если DNS/HTTPS ещё не настроены, для закрытого тестового доступа используйте SSH-туннель и временно `MP_COOKIE_SECURE=false`:

```sh
ssh -L 8080:127.0.0.1:8080 root@203.0.113.10
```

После изменения настроек пересоздайте сервисы командой `docker compose up -d`. Это не запускается автоматически данным документом.

## HTTPS через Nginx Proxy Manager

Если NPM находится в Docker на том же хосте, `127.0.0.1` внутри его контейнера не указывает на панель. Подключите API к существующей сети NPM через прилагаемый override:

```sh
# Добавьте в .env настоящее имя Docker-сети NPM:
# MP_NPM_NETWORK=nginx-proxy-manager_default
docker compose -f compose.yaml -f deploy/compose.npm.yaml up -d --build --wait
```

В NPM создайте Proxy Host для домена панели: схема `http`, адрес `mp-panel`, порт `8080`, Websockets Support включён, SSL сертификат и Force SSL включены. В последующих командах обновления используйте тот же набор Compose-файлов. [NPM описывает общую Docker-сеть для upstream-сервисов](https://nginxproxymanager.com/advanced-config/#best-practice-use-a-docker-network).

Для агентского канала оставьте отдельный публичный 8443 непосредственно до API. Обычный NPM Proxy Host не подходит: TLS завершается на прокси и сертификат агента теряется. Допустим отдельный TCP Stream, который прозрачно передаёт весь TLS до API, с корректно настроенным портом без конфликта публикаций. Внутренний CA и выдаваемые сертификаты сохраняются в `panel-data`.

## Подключение игрового хоста

В панели откройте «Хосты → Подключить хост», задайте IP, SSH-порт и пользователя. Сравните полученный fingerprint с доверенным значением и подтвердите его. Введите SSH-ключ или пароль; при необходимости пароль sudo.

В поле «Адрес игровых портов» задайте локальный IP именно этого игрового хоста либо `0.0.0.0` для всех его IPv4-интерфейсов. Для приватной сети укажите адрес VPN. Адрес панели не переносится на игровые хосты. При повторном подключении сохранённый адрес подставляется в форму; после изменения адреса остановите и снова запустите Minecraft, чтобы контейнер получил новые настройки. Пересоздаётся только контейнер, файлы и мир сохраняются. Прежняя глобальная переменная `MP_GAME_BIND_ADDRESS` больше не используется.

Worker выдаёт отдельный клиентский сертификат, загружает Linux-агент по SFTP, устанавливает systemd-службу и Docker. Задание считается успешным после первого защищённого heartbeat. SSH-секреты шифруются в очереди и удаляются после выполнения или истечения срока; агент дальше работает через исходящее mTLS-соединение.

На игровом хосте находятся:

```text
/usr/local/bin/mp-agent
/etc/mp-agent/config.json
/etc/mp-agent/agent.crt
/etc/mp-agent/agent.key
/etc/mp-agent/ca.crt
/var/lib/mp-agent/
```

Диагностика агента: `systemctl status mp-agent`, `journalctl -u mp-agent -n 100`. Если агент не вышел на связь, проверьте DNS, доступ игрового хоста к `MP_AGENT_PUBLIC_URL`, сертификаты и время машин. В текущей версии повторная регистрация уже установленной другой identity требует явного удаления или перенастройки старого агента администратором.

Далее мастер сервера предложит ядро, Minecraft, совместимые сборки и Java. JAR ядра скачивается автоматически. Свой JAR и дополнительные моды/плагины загружаются через панель. Согласие с EULA даёт пользователь в мастере; установка записывает его согласие.

## Сеть Minecraft

По умолчанию контейнеры публикуют выбранные игровые TCP-порты на игровых хостах. Разные DNS-поддомены с одинаковым IP и портом не маршрутизируются обычным HTTP Proxy Host. Nginx TCP Stream может пересылать игровой порт, но для выбора сервера по Minecraft hostname нужен отдельный Minecraft-aware gateway, например Gate Lite, и приватная сеть между gateway и агентами.

Доступны mc-router и Gate Lite с управлением маршрутами через приватный API без перезапуска шлюза. Настройка описана в [GATEWAY.md](GATEWAY.md); по умолчанию gateway overlay отключён. Внешние серверы подключаются через «Настройки → Игровые домены» по IP:порту без агента. DNS, NAT, VPN и firewall настраиваются отдельно. В режиме без шлюза подключайтесь к IP/домену игрового хоста и назначенному порту. Прямые публичные игровые порты можно закрыть после подготовки шлюза и приватной сети.

## Обслуживание и сохранность

При запуске сервер получает Docker restart policy `unless-stopped`. Работающий сервер автоматически поднимается после перезапуска Docker или хоста, если Docker включён в автозагрузку и сетевой адрес сохранился. Остановка из панели устанавливает `restart=no`, поэтому намеренно остановленный сервер остаётся выключенным. Это поведение [политик перезапуска Docker](https://docs.docker.com/engine/containers/start-containers-automatically/); оно не гарантирует успешный запуск ядра с ошибочными файлами или недоступным IP.

```sh
docker compose ps
docker compose logs --tail 100 api worker
docker compose restart api worker
```

База хранится в volume `mp-panel_database`; секреты, CA и загрузки хранятся в `mp-panel_panel-data`. Сохраняйте оба volume: одна база без ключа `secrets.key` не позволяет расшифровать секреты, а потеря CA нарушает связь агентов. Миры и игровые резервные копии находятся на игровых хостах в `/var/lib/mp-agent`, отдельно от базы панели.

Автоматическая уборка исходных копий загрузок, хранение архивов обновлений и утилита для очистки старой панели описаны в [руководстве по хранению](STORAGE.md). Настройки `MP_UPDATE_BACKUPS` и `MP_PRUNE_BUILD_CACHE` задаются в `.env` и читаются установщиком при обновлении.

Резервную копию PostgreSQL можно сделать через `pg_dump`; файлы panel-data копируйте административным инструментом при остановленных API/worker, сохраняя права. Не публикуйте резервные копии с ключами. Существующие серверы продолжают работать при недоступности панели; управляющие задания ждут доступного агента или заканчиваются по сроку.

При переносе панели на другую машину перенесите базу, panel-data и исходники, настройте внешний URL и переключите DNS. Хранение прежнего CA и hostname позволяет агентам сохранить доверие. Изменение адреса agent API требует обновления конфигурации каждого агента.
